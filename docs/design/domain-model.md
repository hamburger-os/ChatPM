# 领域模型与可信项目状态


## 关键概念（含未实施的目标对象）
| 领域 | 主要对象 | 说明 |
|---|---|---|
| 组织与项目 | Tenant、User、Project、ProjectMember | 项目独立权限，组织可设置策略 |
| 对话 | Room、Message、Attachment | 消息原文/版本和来源引用 |
| 工作管理 | Task、TaskDependency、Milestone | 负责人、期限、状态、依赖及版本 |
| 风险与决策 | Risk、Decision、Approval | 风险登记、升级与确认 |
| AI 分析 | Evidence、AnalysisRun、ProposedChange | 抽取依据、推断与待确认建议 |
| 自动化 | FollowUpPolicy、FollowUpPlan、DeliveryAttempt | 可靠提醒计划与执行轨迹 |
| 知识与报告 | DocumentVersion、ReportSnapshot | 文档版本、统计截点和报告 |
| 基础设施记录 | OutboxEvent、InboxReceipt、AuditEntry | 可靠事件和可追溯变更 |

## 业务事实建立机制
**原始消息/文档 → 证据 Evidence → 候选 ProposedChange → 验证/确认 → 领域命令 → 正式 Task/Risk/Decision。**

- 成员说“差不多完成”并不等于完成，AI 先追问验收标准。
- AI 识别的负责人、期限和风险等级可能是推断；必须与明确承诺区分。
- “自动登记候选”可默认启用；“创建承诺或改变里程碑”由项目策略决定是否人工批准。
- 每个变更可追溯到原始上下文、确认人、版本和执行日志，来源不可访问时不能泄露原文。

## 建议状态
任务：草拟（可选）→ 待开始 → 进行中 / 阻塞 → 完成 / 取消；审批建议为独立生命周期（待确认、接受、拒绝、过期、冲突），**不混入正式任务状态**。

## 数据一致性
正式状态用唯一业务 ID 和 version 控制并发；相关关系有外键/唯一性约束；租户及项目作用域为每次读写的必要条件。删除/修改历史遵循数据保留政策和审计规则。

## 策略方向
系统将按项目策略分级决定 AI 动作；尚未实施的自动转换规则必须先通过服务端授权与领域命令验证，AI 不能代替成员作出正式承诺。

## ADR-022 进度证据与日历日期
`Task.due_date` 为所属项目时区的日历日；只有时间发生的真实证据才继续用 `TIMESTAMPTZ`。 `TaskProgressUpdate` 是只读来源消息关联到正式任务的待审证据（progress / blocker / completion_claim），Owner 的接受动作只使证据可信，不自动把任务判为完成；通过事务和审计记录决定。复杂依赖/里程碑/进度百分比仍需未来清晰建模。

## ADR-030 · 正式项目管理领域对象与业务边界

第一阶段在已有 Task/Risk 旁增加 ProjectGoal（价值目标与成功标准）、Milestone（具有项目时区日历截止日的检查点）、Deliverable（明确验收标准与独立审核）、Issue（已发生问题）、Decision（记录经授权的选择）、ChangeRequest（对项目基线有影响的审批申请）、TaskDependency（同项目有向无环依赖）。领域对象不与 AI 候选表合并，也不把“完成声明”直接改为“验收完成”。

交付物：计划态 → 待验收 → 已验收/退回，审核者不得是提交者本人；状态、责任人、项目作用域、版本均由服务端验证。变更申请：待审批 → 通过/拒绝；审批不隐式修改 Task/Milestone 基线，实际生效必须单独的正式命令。任务依赖只允许同项目存在的任务，不允许自环和循环，插入期间对项目关系图加事务串行锁。

初期正式对象可通过受项目权限约束的 API 管理；Web 专门交互、基线联动、收益计算、全量流程仍后续实现，须在实施状态中明确。新对象不能以空壳表或产品路线图条目冒充完整流程。

### ADR-030 成员历史引用不变量

正式交付物与问题的负责人在**指派当时**必须拥有该项目和组织成员身份（事务内行锁核验）；之后如果人员正常退出项目，历史交付责任、验收者与审计仍保留对 `users` 的有效引用，不通过长期绑定 `project_members` 阻止成员撤权。权限动态验证和历史数据溯源是不同维度：任何后续修改仍须重新授权。

## ADR-031 · 正式项目管理工作台

项目正式登记簿通过 Web 新增「项目治理」页签集中访问，分别显示目标、里程碑、交付物、问题、决策、变更请求及任务依赖，不再让成员通过隐藏 API 才能使用。项目成员只查看已授权项目；owner/manager 负责建计划与登记；交付物指派成员可以提交成果，owner/manager 负责独立验收或退回；只有 owner 可批准其他人提交的关键变更。前端展示角色可用操作只是便利，最终由 API 校验。所有 POST 需生成单次 idempotencyKey，页面重试已完成操作时由服务端幂等机制防重复。尚未实现自动收益评估或基线联动，不在界面伪称 AI 已执行正式变更。

## ADR-036 · 已发生问题 Issue 闭环及不丢历史记录

Issue 是已经发生并影响项目的事实，不是未来可能发生的 Risk。项目 owner/manager 可在同项目内将 Issue 从 `open` 变更为 `resolved`，经确认影响再次出现时可从 `resolved` 重新打开至 `open`；每次均要求明确非空处理说明、预期版本和客户端 UUID 幂等键。

事务内重新检查 actor 的项目及组织成员身份，锁定当前 Issue 行，验证合法转换、当前版本与项目作用域，增加 `version`，写入不可覆写的 `project_issue_transitions` 状态历史。业务状态、历史、审计、DomainEvent、Outbox 和 CommandReceipt 必须原子提交；重试同键同 payload 不增加版本，同键不同 payload 409。成员和 observer 可以查看自己有权访问项目的 Issue 历史，但不能通过仅更换 URL 读取其他项目数据。退出项目后历史操作者仍关联 Users，不因撤权而删除证据。

处理说明是人工确认的项目事实，不由 LLM 直接写入。不同事件的提交/解决记录永久保留在项目数据生命周期内；需要删除时须另行实现合规管理而不是在 UI 隐藏即可消失。当前仍不支持跨项目问题联动、风险自动转 Issue 或 PM Playbook。
