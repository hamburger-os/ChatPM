# AI 项目经理编排设计

**状态：设计基线已审查；实验性 MVP 的候选提取与显式关联澄清已实施。**

## 核心原则
AI 是**受约束的项目协作代理**，而不是拥有数据库管理员权限的自治系统。它提供判断、追问和建议，正式变更由受控业务命令提交。

## 一条 AI 任务的生命周期
事件触发 → 获取被授权项目上下文 → 检索相关正式状态和文档证据 → 模型结构化分析 → 校验模型输出 → 保存 Evidence/ProposedChange → 策略评估 → 自动执行低风险动作或请求人工确认 → 审计与后续跟进。

## AI 的能力边界
- **可自动**：辅助提取信息、生成候选、提醒原有明确承诺、询问缺失字段、制作有来源的报告草稿（均须满足租户策略）。
- **须受控**：创建正式任务、指派责任人、认定任务完成、改变截止时间、改变风险级别、发布外部报告、调整里程碑。
- **禁止默认**：替成员作承诺、绕过权限获取其他项目内容、执行来自聊天消息的任意系统指令、无审批进行不可逆操作。

## 可信上下文
“已确认事实”来自 PostgreSQL；“历史讨论”来自经鉴权消息；“知识参考”来自带版本/来源的文档。不同来源显式区分。模型输出 JSON Schema 校验，异常/低置信度进入人工确认，不将自然语言推断直接变成事实。

## 避免 AI 刷屏
设置触发阈值、同一主题合并、同一问题冷却期、用户主动 @AI 的优先级、项目的安静时间和升级路径。每次追问说明原因、关联对象和所需最少信息。

## 可替换性
模型通过 Provider 接口更换；提示模板/策略版本化。先采用一个受控编排器，不让“观察、决策、执行”多个 Agent 彼此自循环。

## 默认权限策略
第一版**不自动把候选转为正式任务**；也不自动改变负责人、截止时间、完成状态、里程碑和已确认风险。AI 只能生成带来源的候选和草稿，经有权限的成员确认后调用领域命令。不配置模型时显示明确的未启用状态。

## v0.1 现状
管理员/项目负责人明确设置后，Worker 使用配置的外部模型提取单条群聊消息里的候选任务/风险，输出受 JSON Schema 校验并保留来源消息 ID；负责人接受/拒绝后才写正式记录。长对话推理、文档检索、模型路由、误提取评测尚未实现。

## 群聊追问的 MVP 规则
从消息生成候选后，若缺少负责人或截止日期，可自动提出不超过两条具体澄清问题。为了避免刷屏，同一项目近 10 分钟内已经有候选提示则只更新待确认列表、不重复发送聊天提示。回答必须经新消息分析或负责人确认，不能擅自补完原有承诺。下一阶段应将追问与关联任务/问题状态建模为明确会话闭环。

## 显式候选引用的多轮澄清（v0.2）
每个缺少负责人或明确截止日期的 AI 候选任务建立 `ClarificationThread`，AI 在群聊内给出 `【候选:UUID】`。成员回复需包含同一引用，系统仅将模型提取的补充线索保存为 `ClarificationResponse`，保留来源消息、模型和 Prompt 版本，逐条审计并合并到尚未关闭的待确认线程。**不依靠关键词猜测关联，不能自动写正式任务**。负责人在候选页面查看建议、选择项目成员后点击确认；确认任务时采纳该候选经澄清的明确期限，线程关闭。多个回答可继续补充，重复消息幂等，不可更新已关闭候选。无明确候选引用的消息按普通提取处理，尚不支持跨文档/会话语义自动关联。

## 模型边界和预算
`LLMProvider` 由单一 `OpenAIProvider` 实现，对候选与澄清分别使用严格 JSON Schema 和应用层 Zod 校验；服务端按项目/UTC 日期原子预留模型请求计数，默认每天最多 50 次（`AI_DAILY_REQUEST_LIMIT` 可调，允许 1–500）；达到限额时原事件保留到次日，不丢任务，不消耗普通失败次数。模型调用保持项目负责人 opt-in，记录候选 evidence_excerpt、模型/Prompt 版本。尚无逐 token 计费、模型质量评测与自动脱敏；这些属于生产准入条件，不得称为已完成。
