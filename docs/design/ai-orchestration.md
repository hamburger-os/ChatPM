# AI 项目经理编排设计

## 核心原则
AI 是**受约束的项目协作代理**，而不是拥有数据库管理员权限的自治系统。它提供判断、追问和建议，正式变更由受控业务命令提交。

## 一条 AI 任务的生命周期
事件触发 → 获取被授权项目上下文 → 检索相关正式状态和文档证据 → 模型结构化分析 → 校验模型输出 → 保存 Evidence/ProposedChange → 策略评估 → 自动执行低风险动作或请求人工确认 → 审计与后续跟进。

## AI 的能力边界
- **可自动**：辅助提取信息、生成候选、提醒原有明确承诺、询问缺失字段、制作有来源的报告草稿（均须满足租户策略）。
- **须受控**：创建正式任务、指派责任人、认定任务完成、改变截止时间、改变风险级别、发布外部报告、调整里程碑。
- **禁止默认**：替成员作承诺、绕过权限获取其他项目内容、执行来自聊天消息的任意系统指令、无审批进行不可逆操作。

## 可信上下文
“已确认事实”来自 PostgreSQL；“历史讨论”来自经鉴权消息；“知识参考”来自带版本/来源的文档。不同来源显式区分。模型输出 JSON Schema 校验，异常/低置信度进入人工确认，不将自然语言推断直接变成事实。

## 避免 AI 刷屏
设置触发阈值、同一主题合并、同一问题冷却期、用户主动 @AI 的优先级、项目的安静时间和升级路径。每次追问说明原因、关联对象和所需最少信息。

## 可替换性
模型通过 Provider 接口更换；提示模板/策略版本化。先采用一个受控编排器，不让“观察、决策、执行”多个 Agent 彼此自循环。

## 默认权限策略
第一版**不自动把候选转为正式任务**；也不自动改变负责人、截止时间、完成状态、里程碑和已确认风险。AI 只能生成带来源的候选和草稿，经有权限的成员确认后调用领域命令。不配置模型时显示明确的未启用状态。

## 当前模型编排能力与限制

已提供外部模型 Provider、Schema + Zod 双层结构验证、每项目每日请求次数限额、候选任务/风险提取与显式 `【候选:UUID】` 澄清。候选和补充线索保存来源消息及模型/Prompt 版本，只有项目负责人可以确认正式事项。

当前支持唯一近期澄清追问的谨慎自然语言关联，但仍不支持任意多线程自由关联、长期项目记忆、真实模型质量评测、本地推理或精确 token 成本控制。项目策略分级自动执行、提供商专有协议和实际本地模型兼容性验收属于后续目标，不得越过当前服务端人工审批约束。

## 可配置模型传输与边界（ADR-019）

- **目标**：部署者通过服务端环境配置 OpenAI、DeepSeek 或其它符合已实现协议的模型，不让供应商选择渗透业务审批流程。
- **设计**：保留一个受控 LLMProvider 和原有请求配额；独立传输实现支持 `responses`（JSON Schema）与 `chat-completions`（JSON Object + Zod）。四个部署变量：`LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_STYLE`。不维护旧 `OPENAI_*` 兼容层。
- **数据流**：Owner 授权启用 → Worker → 预留项目 UTC 日额度 → 配置的单一模型端点 → 结构化校验 → 有来源的候选或澄清 → Owner 审批。不得直接提交正式工作记录。
- **失败与安全**：配置 URL 仅由部署管理员控制；仅允许绝对合法 HTTP(S) URL，外部必须 HTTPS；密钥不能传入 Web、日志或审计正文；非 2xx、超时、拒答、截断、非 JSON、类型错误立即失败，不自动无提示切换服务商。
- **边界及取舍**：不引入通用 AI Gateway、多厂商 SDK、数据表或密钥管理 UI。HTTP 本机推理仅供可信部署环境，容器需显式设置可达的内部地址。未完成真实模型质量、费用、隐私和生产安全验收。
- **验收**：两种协议模拟请求/回复、失败模式及 URL/Key 配置测试，数据库集成的日额度与重放保持不变，中英文部署指南和 Docker 变量同步。

### 审查追加的模型安全闭环（ADR-019）

项目启用 AI 的 API 操作必须使用和 Worker 相同的 `readLLMSettings` 配置验证，杜绝前台检查旧密钥而后台读取新密钥。模型 HTTP 禁止自动跟随重定向（可能跨 HTTPS/内网边界泄漏请求正文）。候选和澄清既有 `model_name` 字段存储“模型 ID + 端点主机 + 协议 + Base URL 非可逆指纹”的组合身份；不存 Key、URL path 或 query，切换代理路径/模型后仍可区分，避免新表/不可逆 SQL 改造。真实提供商可靠性、供应商治理和内部地址曝光仍需部署者评估。

## ADR-021 · 可持续协作的受控 AI 项目经理（2026-10-13）

### 问题与取舍
实机测试证明此前存在五项缺口：发送按钮窄到折行；“AI/提醒”耦合难用；模型凭证只能编辑服务端环境且不能测试；模型每次仅分析单消息，没有推理/上下文预算选项；澄清必须手输 UUID 且 10 分钟抑制使用户感到被忽略。目标是**单个受限 PM Agent**，而非多自治 Agent；保留现有 PostgreSQL、Owner 审批、Outbox 和证据完整性。不引入 Pi 编程代理/任意 Shell 访问，参考其分层模型、会话与压缩理念，在真实 API 兼容性、授权和成本评测足够时复审 SDK 替换。

### 系统模型配置与安全边界
- 每项目 Owner 可以在设置页选择 `server`（由部署管理员的 `LLM_*` 环境变量控制）、`openai` 或 `deepseek`；后两者采用**内置固定 HTTPS 端点**，不允许项目客户端提供任意 URL，减少 SSRF/内网访问和多租户越权。Owner 可以保存/轮换项目独立 API Key，数据库只保存 AES-256-GCM 密文；使用从服务器 SESSION_SECRET 派生的密钥，并限制密钥文件/数据库访问。此选择意味着更换 SESSION_SECRET 前必须重新录入这些项目密钥；长期需改为独立 KMS。
- 可配置模型 ID、非负推理强度（只有支持的 Provider 发送相应参数）、响应 Token 限额和输入字符预算；UI 展示协议、端点、模型、Key 是否存在，绝不回显或向浏览器提供真实 Key。部署级 server 模式不能在 UI 编辑密钥或目标 URL。
- Owner 发起测试连接：只发送固定的非敏感 JSON 探测句，API 限频、成功时返回结构化兼容状态/耗时，不返回第三方原文或凭证；不计入业务消息提取。真实计费需用户知悉。
- 项目 Owner 显式启用后才能分析用户消息。禁用时不调用外部模型，项目数据不能跨项目传递。AI 配置更新写审计、变更后的请求读取当前配置。

### 连续对话与上下文
- 每条分析读取**同项目**最近有界消息、正式任务/风险和待澄清候选；按角色和证据类型分层组装，给定输入预算，优先保留当前消息和关键状态，对旧讨论做确定性的裁剪而不是让无依据的 AI 摘要覆盖正式事实。模型生成的任务/风险仍需人工批准。
- 关联澄清：显式引用优先；UI 提供针对候选的回复入口（结构化关联）；无引用时只在唯一、最近的活动澄清问答且消息明显含补充线索的情况下自动关联，否则保持普通消息，绝不猜测目标。用户反馈必须区别“分析中”“无新建议”“候选已生成”“补充已记录”“失败待重试”，避免静默。
- 用户可使用 `@AI` 请求只读状态问答；模型的回复不得修改正式事实；自动消息提取不等于开放的通用对话 Agent。所有 AI 活动记录最少包括来源消息、状态、模型身份、错误代码、时间，访问需项目权限控制。
- Agent 预置只读项目事实查询，不提供文件 Shell、浏览器或第三方任意权限；项目变更全部通过领域审批命令。后续长时证据摘要、真正 Token compaction 和多模型故障切换需基准测试。

### 验收
Windows/Linux/Docker 同一迁移和 Worker；跨项目授权及 Key 不外泄、无任意 URL、API 测试限频、重复 Outbox、不带 UUID 的单线程澄清、歧义不自动关联、相对日期不猜年份、非候选有状态、手动 @AI 答复、消息按钮响应式布局、提醒不依赖 AI。模拟 API CI 不能冒充真实 DeepSeek/Pi 集成验证。

## ADR-022 已有任务关联与项目经理式跟进
处理管线从“普通消息一律抽取新候选”改为“优先根据**同项目有边界的正式任务目录**识别已存在工作→记录待审批的进度证据，或提出新的任务/风险候选”。模型只能选择本次授权的任务 ID，业务层重新核对项目所有权和任务状态。对歧义匹配或轻微语义类似但没有证据的输入，不自动合并；对“已完成方案初稿”仅标注阶段成果，不将正式任务标记 done。进度证据通过任务详情和审核列表展示，待 Owner 批准后才成为可信进度事实。用户主动 @AI 仍只读。
