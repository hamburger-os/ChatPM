# 主动跟进、提醒与风险升级

**状态：设计基线已审查；基础提醒已在实验性 MVP 实施。**

## 跟进计划
每个需跟进的任务拥有可持久化的 FollowUpPlan：跟进原因、对象、触发时间、当前任务版本、策略和状态。Redis/BullMQ 用于分发执行，数据库保存真实计划与投递记录。

## 典型规则
| 情况 | 默认方案方向 |
|---|---|
| 临近截止且未完成 | 按项目配置提醒负责人 |
| 已超过截止日期 | 先确认实际进度与阻塞，再按严重度升级 |
| 成员回答“完成差不多” | 追问交付物及验收结果，不直接关闭任务 |
| 依赖任务阻塞 | 向依赖负责人确认影响和预计恢复时间 |
| 长期没有反馈 | 采用冷却和合并策略，不重复刷屏 |
| 需要管理层决策 | 生成待决事项并通知授权决策人 |

## 执行步骤
到期扫描 → 原子领取计划 → 读取**最新**任务和成员/审批状态 → 检查工作时间、时区、节假日、冷却、限频和接收偏好 → 按策略选择聊天提醒、重排或升级 → 记录 DeliveryAttempt。

## 可靠性
根据 task_id、规则、任务版本和计划窗口构造幂等键；取消或重排旧任务，发送前再次验证。失败自动退避；重复消息不得产生两次外部通知。发送与外部成功之间不可完全原子化，需要供应商幂等支持或可核对的投递状态。

## 需要审查的产品参数
默认静默时间、提醒提前量、连续催办的最低间隔、升级阈值、节假日来源、是否允许私信。全部按租户/项目配置，**不在当前设计中伪造固定值**。

## 默认行为
项目未配置负责人、截止日期、工作时区/时间和冷却策略时，系统仅记录待跟进建议，不向个人发送自动催办。项目负责人成立默认工作时间与提醒阈值后才启用定时提醒；停止/取消任务立即使相关计划失效。

## v0.1 现状
FollowUpPlan 持久保存在 PostgreSQL，由 Worker 轮询。只有存在负责人、截止日期且项目已经配置工作时段/冷却的任务才启用；站内发送前复核任务版本与工作日。外部私信、节假日、复杂升级、失败告警尚未实现。

## 冷却窗口与重排安全（2026-10-12）
任务负责人、截止时间、状态或项目策略变化会重算 FollowUpPlan，但**不应绕过已发送提醒的冷却期限**。`syncFollowup` 使用上次发送时间与当前冷却配置的下限，并与新计算的触发时间取较晚者；停止/取消仍立即关闭计划。站内投递对重复 nonce 不重复记录成功审计。提醒仍缺少节假日和复杂升级策略。

## 事件级可靠性升级（v0.2）
Outbox 使用数据库原子领取 + 五分钟租约，最长八次交付，失败按指数退避（上限一小时），保存脱敏的错误类别而非包含客户消息的异常原文。第八次失败或最后领取者崩溃且租约过期时，事件进入隔离状态，按项目仅向负责人显示；负责人审核后可人工重放并写审计。每日模型限额采取次日继续而非死信。事务内候选/AI 消息按事件/消息来源去重；仍采用至少一次执行语义，不能宣称任何外部调用 exactly once。
