# 聊天、消息与可靠事件

## 消息主流程
**当前流程：** 成员发送消息 → 服务端校验项目成员权限与输入 → PostgreSQL 同事务写入 Message + OutboxEvent → 返回已持久化状态 → Web 通过 `after=seq` 增量轮询 → Worker 在项目启用 AI 后处理分析。当前没有 Room 实体和实时广播。

**未来实时推送：** 即使 SSE/WebSocket 断线，客户端也必须按项目提交顺序游标补拉；推送仅加速通知，不作为可靠消息存储。

## 消息模型
**当前字段：** 作者、项目、幂等 nonce、序号、时间、类型与正文。**目标扩展：** 房间、引用关系、附件引用及编辑/撤回版本；不得将这些目标视为现有数据库字段。

## 事件与失败恢复
业务写入与 Outbox 在同一数据库事务，异步发布后由消费者处理。至少一次投递意味着**可能收到重复事件**，因此 AI 分析触发、通知及领域变更必须使用幂等键。重试超限进入隔离队列，管理员可重放/处置。

## AI 参与策略
AI 不需要回复每条消息：优先合并短时间连续对话、识别有价值事件，按消息与任务相关性决定抽取；对闲聊保持安静。高频群聊应有批处理节流与模型费用上限。

## 取舍
初期只支持站内群聊，不实现第三方 IM 双向一致性。后续渠道适配须携带外部消息 ID、来源时间和授权映射。

## 当前消息与事件保证

消息写入使用项目级事务 advisory lock，确保增量游标的提交顺序；`client_nonce` 防止重复写入。请求按项目权限过滤，首次拉取最近 200 条，随后按 `after` 增量读取。

Outbox 是至少一次投递：UUID claim token 防止过期消费者回写、失败指数退避、死信隔离和受权重试。未知事件类型应显式失败并告警，不能被静默标记成功。尚无完整的双向历史分页、WebSocket/SSE 和附件。

## ADR-025 · 小团队轮询预算与实时升级门槛（2026-10-14）

- 当前单页消息 5 秒短轮询、工作台同时查询任务/成员/风险/候选/进度/报告六个端点，打开多个页签与多个用户可放大请求量；反向代理可能让来源 IP 看起来相同。
- 临时可靠性方案：非实时工作台降低至 15 秒刷新，页面不可见时暂停并在恢复可见时补查；避免并发重叠拉取。保持现有消息游标与项目权限不变量，不增加无事实价值的缓存数据层。
- API 的全局通用限流不得把已经合法登录的不同人员压进同一个不可区分的代理 IP 桶；登录/注册端点仍需要更严的 IP 限流。租户与项目授权仍在后端，任何限流键不是身份鉴权依据。
- 后续 SSE 应经同源流式代理、带事件 ID 的持久增量读取、断线补偿、鉴权撤销与压力测试后再交付，不应仅增加易丢通知的内存广播；本阶段不声称实时消息已实现。
- 验收：多个成员同网关同时查看项目不会因前端自身轮询触发大量 429；页面后台暂停任务轮询，回前台恢复；项目切换不出现旧项目结果覆盖。

## ADR-065 · 用户消息事务授权与单一写入入口

用户发言必须通过 Conversation Core 的 `postUserMessage`；当前组织与项目成员锁、`message.write` 权限、项目级序号锁、Message、Outbox 和最小审计都在一个 PostgreSQL 事务内。相同作者/内容/nonce 的重试返回原结果而不重复产生事件，内容或作者不同则 409；撤权后的旧重试也必须重新授权。Worker 的 AI/提醒系统消息使用受控 `insertMessage`，不能冒充 HTTP 用户身份。SSE、删除和消息编辑仍未实现。
